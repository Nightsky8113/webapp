## 🏗️ アーキテクチャ概要

### アーキテクチャパターン

このアプリケーションは**モジュラーアーキテクチャ**と**サービス層パターン**を採用しています。

```
Presentation Layer (pages/, components/)
    ↓
Business Logic Layer (services/, utils/)
    ↓
Data Access Layer (services/supabase.js, services/dataService.js)
    ↓
External Services (Supabase, Overpass API)
```

### SPA（Single Page Application）設計

- **クライアントサイドルーティング**: ハッシュベース（`#/home`）を使用
- **動的コンテンツ読み込み**: ページ遷移時にJavaScriptでコンテンツを生成
- **テンプレートエンジン**: 独自実装の簡易テンプレートシステム

**選定理由**:
- フレームワーク依存を避け、軽量化
- 学習コストの削減
- バンドルサイズの最小化

## 🛠️ 技術スタックの選定理由

### フロントエンド

#### Vanilla JavaScript
- **理由**: フレームワークオーバーヘッドの排除、学習コストの削減
- **トレードオフ**: コード量の増加、状態管理の手動実装

#### Vite
- **理由**: 高速なHMR、ES Modules対応、軽量
- **代替案検討**: Webpack（設定が複雑）、Parcel（カスタマイズ性が低い）

#### UnoCSS
- **理由**: Tailwind CSS互換、オンデマンド生成、カスタムクラス対応
- **代替案検討**: Tailwind CSS（設定が複雑）、Pure CSS（保守性が低い）

### バックエンド

#### Supabase
- **理由**: 完全マネージド、PostgreSQL、リアルタイム機能、無料枠あり
- **代替案検討**: Firebase（NoSQL、学習コスト高）、自前構築（運用コスト高）

#### Overpass API
- **理由**: 無料、OpenStreetMapデータ、店舗情報が豊富
- **代替案検討**: Google Places API（コスト高）、Foursquare API（制限が厳しい）

## 📁 ディレクトリ構造と設計思想

### レイヤー分離

```
src/
├── pages/          # Presentation Layer - UI表示ロジック
├── components/     # Presentation Layer - 再利用可能なUI部品
├── services/       # Business Logic + Data Access Layer
├── utils/          # Cross-cutting Concerns (横断的関心事)
├── templates/      # View Layer - HTMLテンプレート
└── styles/         # View Layer - スタイル定義
```

### 設計原則

1. **関心の分離（Separation of Concerns）**
   - HTML（templates/）、CSS（styles/）、JavaScript（pages/, components/）を明確に分離

2. **単一責任の原則（Single Responsibility Principle）**
   - 各ファイルは1つの責任のみを持つ
   - 例: `dataService.js`はデータ取得のみ、`storageService.js`は画像管理のみ

3. **DRY（Don't Repeat Yourself）**
   - 共通処理は`utils/`に集約
   - 再利用可能なUIは`components/`に分離

4. **依存性逆転の原則（Dependency Inversion Principle）**
   - 高レベルのモジュール（pages/）が低レベルのモジュール（services/）に依存
   - 抽象化レイヤー（`storeSearchService.js`）で実装を切り替え可能

## 📄 主要ファイルの詳細説明

### コアアーキテクチャ

#### `src/router.js`

**設計パターン**: Strategy Pattern + Observer Pattern

```javascript
// Strategy Pattern: ルートごとに異なるレンダリング戦略
const routes = {
    '/home': { render: HomePage, attachEvents: attachHomePageEvents },
    // ...
};

// Observer Pattern: hashchangeイベントを監視
window.addEventListener('hashchange', () => {
    renderPage(userLocation);
});
```

**実装の詳細**:
- ルートマッチングアルゴリズム: 線形探索（O(n)）- ルート数が少ないため
- パラメータ抽出: 動的パラメータ（`:storeId`）を正規表現ではなく文字列分割で処理
- クエリパラメータ解析: URLSearchParamsを使用（ブラウザネイティブAPI）

#### `src/services/dataService.js`

**設計パターン**: Repository Pattern + Cache-Aside Pattern

```javascript
// Cache-Aside Pattern
export async function getStores(forceRefresh = false) {
    // 1. キャッシュをチェック
    if (!forceRefresh && isCacheValid('stores')) {
        return cache.stores;
    }
    
    // 2. データソースから取得
    const { data, error } = await supabase.from('stores').select('*');
    
    // 3. キャッシュに保存
    cache.stores = data;
    cache.cacheTime.stores = Date.now();
    
    return data;
}
```

**キャッシュ戦略**:
- **TTL（Time To Live）**: 5分
- **キャッシュキー**: データ型ごと（'stores', 'flyers', etc.）
- **無効化**: 明示的な`clearCache()`呼び出し、またはTTL経過

**パフォーマンス最適化**:
- メモリキャッシュ（インメモリ）でI/Oを削減
- キャッシュヒット時のレスポンスタイム: <1ms
- キャッシュミス時のレスポンスタイム: 100-500ms（ネットワーク依存）

### サービス層

#### `src/services/storeSearchService.js`

**設計パターン**: Strategy Pattern + Adapter Pattern

```javascript
// Strategy Pattern: APIプロバイダーを切り替え可能
const API_PROVIDER = import.meta.env.VITE_STORE_SEARCH_API || 'overpass';

export async function searchNearbyStores(lat, lng, radius) {
    switch (API_PROVIDER) {
        case 'overpass':
            return await searchWithOverpass(lat, lng, radius);
        case 'google':
            // 将来の実装: Google Places API
            return await searchWithGooglePlaces(lat, lng, radius);
        default:
            throw new Error(`Unknown API provider: ${API_PROVIDER}`);
    }
}
```

**抽象化の利点**:
- 実装の切り替えが容易
- テスト時のモック実装が容易
- 複数のAPIプロバイダーに対応可能

#### `src/services/storageService.js`

**設計パターン**: Facade Pattern

```javascript
// Facade Pattern: 複雑なSupabase Storage操作をシンプルなAPIで提供
export async function uploadAndSaveFlyer(storeId, file, options = {}) {
    // 1. ファイル検証
    validateImageFile(file);
    
    // 2. Storageにアップロード
    const uploadResult = await uploadFlyerImage(file);
    
    // 3. データベースに保存
    const dbResult = await createFlyer({
        store_id: storeId,
        image_url: uploadResult.publicUrl,
        // ...
    });
    
    return dbResult;
}
```

**エラーハンドリング**:
- 各ステップでエラーをキャッチ
- ロールバック処理（アップロード成功後、DB保存失敗時は画像削除を検討）

### ユーティリティ

#### `src/utils/template.js`

**設計パターン**: Template Method Pattern

**実装の詳細**:
- 変数置換: `${key}` → 正規表現 `/\$\{([^}]+)\}/g`
- 条件分岐: `${if:key}...${endif}` → 再帰的なパース
- ループ: `${each:array}...${endeach}` → 配列の各要素でテンプレートを展開

**制限事項**:
- ネストされた条件分岐は未対応
- 変数のスコープはグローバルのみ

**パフォーマンス**:
- テンプレートは一度だけ読み込まれ、メモリにキャッシュ
- 変数置換は文字列操作のみ（高速）

#### `src/utils/map.js`

**設計パターン**: Module Pattern

**Leaflet.js統合**:
- グローバルなマップインスタンスを1つだけ管理
- マーカー管理: Mapオブジェクトでマーカーのライフサイクルを管理
- メモリリーク防止: ページ遷移時にマーカーをクリア

## 🔄 データフローと状態管理

### 状態管理戦略

このアプリケーションは**状態管理ライブラリを使用していません**。代わりに以下を使用:

1. **URL状態**: ページ情報、検索クエリ、フィルター条件
2. **LocalStorage**: 位置情報、お気に入り（永続化）
3. **メモリキャッシュ**: データベース取得結果（一時的）
4. **DOM状態**: フォーム入力、UIの表示/非表示

### データフロー図

```
User Action
    ↓
Event Handler (attachEvents)
    ↓
Service Layer (dataService, storageService)
    ↓
API Call (Supabase, Overpass API)
    ↓
Data Transformation (utils/)
    ↓
Template Rendering (template.js)
    ↓
DOM Update
```

### 状態の永続化

| 状態 | 保存先 | 有効期限 | 理由 |
|------|--------|----------|------|
| 位置情報 | LocalStorage | 無期限 | ユーザー体験向上（位置情報取得の省略） |
| お気に入り | LocalStorage | 無期限 | ユーザーデータの永続化 |
| データベースキャッシュ | メモリ | 5分 | パフォーマンス向上 |
| APIキャッシュ | メモリ | 30分 | レート制限回避 |

## ⚡ パフォーマンス最適化

### 1. コード分割

```javascript
// 動的インポート: 必要な時だけ読み込む
const { requestUserLocation } = await import('../utils/location.js');
```

**効果**:
- 初回ロード時間の削減
- 不要なコードのバンドルサイズ削減

### 2. キャッシュ戦略

- **データベースクエリ**: 5分間メモリキャッシュ
- **APIリクエスト**: 30分間メモリキャッシュ
- **テンプレート**: 読み込み後メモリに保存

### 3. レンダリング最適化

```javascript
// Promise.allで並列処理
const storesHTMLPromises = stores.map(async store => 
    await StoreCard(store, flyer, distance)
);
const storesHTML = (await Promise.all(storesHTMLPromises)).join('');
```

**効果**:
- 順次処理: O(n)時間
- 並列処理: O(1)時間（理想的な場合）

### 4. 画像最適化

- **Lazy Loading**: `loading="lazy"`属性
- **Thumbnail URL**: サムネイルとフルサイズを分離
- **CDN**: Supabase StorageのCDN配信

### 5. イベントデリゲーション

```javascript
// ❌ 悪い例: 各要素にリスナーを追加
stores.forEach(store => {
    document.getElementById(`store-${store.id}`)
        .addEventListener('click', handleClick);
});

// ✅ 良い例: 親要素に1つだけリスナー
container.addEventListener('click', (e) => {
    const card = e.target.closest('[data-store-id]');
    if (card) handleClick(card);
});
```

**効果**:
- メモリ使用量の削減
- 動的に追加される要素にも対応

## 🛡️ エラーハンドリング戦略

### エラーハンドリングの階層

1. **グローバルエラーハンドラー** (`main.js`)
   ```javascript
   window.addEventListener('error', (event) => {
       console.error('グローバルエラー:', event.error);
   });
   ```

2. **非同期エラーハンドラー** (`main.js`)
   ```javascript
   window.addEventListener('unhandledrejection', (event) => {
       console.error('未処理のPromise拒否:', event.reason);
   });
   ```

3. **ページレベルのエラーハンドリング** (`router.js`)
   ```javascript
   try {
       html = await route.render(...params);
   } catch (error) {
       // エラーUIを表示
   }
   ```

4. **サービスレベルのエラーハンドリング** (`dataService.js`)
   ```javascript
   if (error) {
       console.error('店舗取得エラー:', error);
       return []; // 空配列を返してクラッシュを防ぐ
   }
   ```

### エラーの種類と対応

| エラー種類 | 発生箇所 | 対応方法 |
|-----------|---------|---------|
| ネットワークエラー | API呼び出し | エラーメッセージ表示、リトライ可能なUI |
| データ不整合 | データベース | デフォルト値の使用、エラーログ |
| テンプレート読み込み失敗 | template.js | フォールバックHTMLの表示 |
| 位置情報取得失敗 | location.js | エラーメッセージ、デフォルト位置の使用 |

### エラー回復戦略

1. **Graceful Degradation**: エラーが起きてもアプリは動作し続ける
2. **Fallback UI**: エラー時は代替UIを表示
3. **User Feedback**: ユーザーにエラーを通知（アラート、トーストなど）

## 🔐 セキュリティ対策

### 1. XSS対策

```javascript
// HTMLエスケープ（utils/helpers.js）
export function escapeHtml(text) {
    const div = document.createElement('div');
    div.textContent = text;
    return div.innerHTML;
}
```

**適用箇所**: ユーザー入力、データベースから取得したデータの表示

### 2. 環境変数の管理

- `.env`ファイルは`.gitignore`に追加
- 環境変数はビルド時に注入（Vite）
- 本番環境ではVercelの環境変数機能を使用

### 3. Row Level Security (RLS)

SupabaseのRLSポリシーでデータアクセスを制限:

```sql
-- 誰でも読み取り可能
CREATE POLICY "Allow public read access" 
ON storage.objects FOR SELECT 
USING (bucket_id = 'flyer-images');

-- 認証済みユーザーのみ書き込み可能
CREATE POLICY "Allow authenticated uploads" 
ON storage.objects FOR INSERT 
WITH CHECK (bucket_id = 'flyer-images' AND auth.role() = 'authenticated');
```

### 4. 入力値検証

```javascript
// 画像ファイルの検証（storageService.js）
function validateImageFile(file) {
    const MAX_SIZE = 10 * 1024 * 1024; // 10MB
    const ALLOWED_TYPES = ['image/jpeg', 'image/png', 'image/webp'];
    
    if (file.size > MAX_SIZE) {
        throw new Error('ファイルサイズが大きすぎます');
    }
    if (!ALLOWED_TYPES.includes(file.type)) {
        throw new Error('対応していないファイル形式です');
    }
}
```

## 🚀 拡張性と保守性

### 新しい機能を追加する場合

#### 新しいページを追加

1. `src/pages/NewPage.js`を作成
2. `src/templates/pages/new-page.html`を作成
3. `src/router.js`にルートを追加
4. `attachNewPageEvents()`関数を実装

#### 新しいAPIプロバイダーを追加

1. `src/services/newApi.js`を作成
2. `src/services/storeSearchService.js`にケースを追加
3. 環境変数で切り替え可能に

#### 新しいデータ型を追加

1. `src/services/dataService.js`に取得関数を追加
2. キャッシュに新しいキーを追加
3. マイグレーションファイルを作成（`supabase/migrations/`）

### コードの品質管理

#### コメント規約

```javascript
/**
 * 関数の目的と意図を説明
 * @param {Type} paramName - パラメータの説明
 * @returns {Type} 戻り値の説明
 */
```

**原則**: コードの翻訳ではなく、**「なぜ」そのコードを書いたか**を説明

#### 命名規則

- **関数**: 動詞で始まる（`getStores`, `renderPage`）
- **変数**: 名詞（`stores`, `userLocation`）
- **定数**: 大文字スネークケース（`CACHE_DURATION`）
- **ファイル**: パスカルケース（`StoreCard.js`, `HomePage.js`）

### テスト戦略（将来実装）

- **Unit Tests**: ユーティリティ関数（`utils/`）
- **Integration Tests**: サービス層（`services/`）
- **E2E Tests**: ページフロー（`pages/`）
